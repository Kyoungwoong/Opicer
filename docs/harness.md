# 개발용 멀티에이전트 하네스

Opicer를 개발할 때 Claude가 역할을 나눠 일하는 구조다. Anthropic의 [Harness design for long-running apps](https://www.anthropic.com/research/harness-design-long-running-apps)에서 가져왔다. 앱이 실행 중에 쓰는 기능이 아니라 **개발 방식**이다.

## 왜 나누나

글에서 짚은 두 가지 문제를 막는다.
- **긴 작업에서 맥락이 흐려진다.** 역할마다 새 맥락에서 일하고, 필요한 것은 파일로 넘긴다.
- **자기 결과물을 후하게 평가한다.** 만든 사람과 검사하는 사람을 분리하고, 검사자를 회의적으로 보정한다.

## 구성

| 파일 | 역할 |
|---|---|
| `.claude/agents/opicer-planner.md` | 짧은 요청을 제품 관점의 계획(범위·시나리오·완료 조건)으로 키운다. 세부 기술은 정하지 않는다. 계획 단계의 기술 결정은 틀리기 쉽고, 그 오류가 구현까지 번지기 때문이다 |
| `.claude/agents/opicer-builder.md` | 합의된 계약서대로 TDD로 구현하고 작게 커밋한다. 계약 밖은 건드리지 않는다 |
| `.claude/agents/opicer-evaluator.md` | 테스트 실행, 앱을 띄워 브라우저로 직접 사용, API·DB 상태 확인 후 기준별로 채점한다. 코드는 고치지 않는다 |
| `.claude/skills/opicer-harness/SKILL.md` | 메인 세션(조율자)이 따르는 흐름. `/opicer-harness <요청>`으로 시작한다 |
| `.harness/<id>/` (git 미추적) | 에이전트끼리 주고받는 파일: `spec.md`, `contract.md`, `build-notes.md`, `qa-rN.md`, `calibration.md` |

## 흐름 (AGENTS.md §3.5 안에서)

```
요청 ─▶ (L) planner → spec.md ─▶ plan.md ─▶ [사용자 OK] ─▶ 이슈·브랜치
     ─▶ contract.md(완료 조건 + 확인 방법) ◀─▶ evaluator 합의(AGREED)
     ─▶ builder 구현·커밋 → build-notes.md
     ─▶ evaluator QA → qa-rN.md ──FAIL──▶ builder 수정 (최대 3회, 넘으면 사용자에게)
                               └─PASS──▶ PR → GitHub 리뷰 코멘트 → CI(ci-pass) → 머지
```

계획 승인, 이슈, 브랜치, GitHub 리뷰 루프, 머지 규칙은 그대로다. 하네스는 그 사이의 구현과 검증을 나눠 맡을 뿐이다.

## 크기별 사용

글의 조언대로 필요한 만큼만 쓴다. 각 단계는 "모델이 혼자서는 이걸 잘 못 한다"는 가정이기 때문이다.

| 크기 | 예 | 흐름 |
|---|---|---|
| S | 문서, 설정, 문구, 한 곳 수정 | 하네스 없이 평소대로 |
| M | 한 영역(API만 또는 웹만) 기능 | 계약 → builder → evaluator QA 1회 |
| L | 백엔드 + 웹, 새 사용자 흐름, 위험한 변경 | planner → 계약 → builder ⇄ evaluator(최대 3회) |

L은 오래 걸리고 토큰을 많이 쓴다. 글에서는 앱 하나에 수 시간, 수백 달러가 들었다. 그래서 시작 전에 사용자에게 알린다.

## 사용자가 쓸 수 있는 명령

정해진 문장일 필요는 없다. 비슷한 뜻이면 된다.

| 명령 | 하는 일 |
|---|---|
| `/opicer-harness <요청>`, "하네스로 해줘" | 크기(S/M/L)를 정하고 이유를 먼저 말한 뒤 진행 |
| "하네스 없이", "S로" | 지금까지 방식 그대로(계획 → PR → 리뷰) |
| "M으로" / "L로" | 크기 지정. L은 시작 전에 비용 안내와 확인 |
| "기획만 해줘" | planner가 범위·시나리오·완료 조건만 정리 |
| "계약서만 써줘" | 계약서를 쓰고 평가자와 합의까지만 |
| "QA만 돌려줘", "PR #N QA해줘" | 지금 브랜치나 그 PR을 평가자가 검사하고 보고서만 씀 |
| "QA 한 번만", "QA 최대 N번" | 구현 ⇄ QA 반복 횟수(기본 최대 3) |
| "고치지 말고 보고만" | 실패가 나와도 자동 수정 없이 보고서만 |
| "계약서 보여줘", "QA 보고서 보여줘" | 최신 파일 요약 |
| "비용 알려줘" | 에이전트별 토큰·시간 |
| "평가자가 놓쳤어: …" | 그 유형을 평가자 보정 예시에 추가(PR) |
| "평가 기준 바꿔줘: …" | 기준 수정(PR) |

## 평가자 보정

글에서 평가자는 처음에 물렀다. 문제를 찾고도 스스로 통과시켰고, 겉핥기로 테스트했다. 그래서 아래 장치를 둔다.
- 프롬프트에 "문제를 찾으면 그 기준은 실패다. 스스로 설득해 넘기지 않는다"를 넣었다.
- 이 저장소의 리뷰에서 실제로 잡은 버그를 보정 예시로 넣었다.
  - 이름 결합 끊김(#155), 다른 경로로 남는 상태(#157), 시각 문자열 정렬(#159), 안내 문구와 규칙 불일치(#159)
  - 잘못된 이유로 실패하는 설정(#163), 빠진 배포 검증(#163), 생명주기 경쟁(#151)
- 평가자가 놓친 버그가 리뷰나 사용자에게서 나오면, 그 유형을 보정 목록에 한 줄로 더한다(`calibration.md` → 프롬프트).
- 새 모델이 나오면 구성 요소를 하나씩 빼 보고, 결과를 바꾸는 것만 남긴다.

## 제약

- 평가자는 브라우저로 화면을 확인하지만, 실제 계정으로 로그인하지 않는다. 비밀값을 넣거나 토큰을 위조하지도 않는다. 로그인이 필요한 화면은 API 테스트나 임시 확인 페이지로 검증한다.
- 소리는 들을 수 없다. 음성 품질은 사람이 확인한다.
